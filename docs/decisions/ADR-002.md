# ADR-002: Server Components, Caching, and Client Data Layer

- Status: Accepted
- Date: 2026-07-30
- Owners: Admin (platform owner)

## Context

Without explicit data-fetching rules, App Router apps often drift into:

- Client-side `useEffect` fetching everywhere
- Full layout remounts on navigation (sidebar reset / flicker)
- Uncontrolled refetching and duplicate API calls
- Slow perceived performance on low-end devices (Congo mobile-first)

## Decision

### 1. Server Components by default

- Everything is a Server Component unless `"use client"` is required (interactivity, browser APIs, TanStack Query hooks).
- Prefer server data fetching; avoid client-side fetching as the default.
- Do not use `useEffect` to load primary page data.

### 2. Route-level caching

Control Next.js caching explicitly:

| Page | Strategy |
|---|---|
| Dashboard | `export const revalidate = 60` |
| Customers | `export const revalidate = 60` (may raise to 300 later) |
| Campaigns | `export const revalidate = 60` |
| Settings | `export const revalidate = 60` |
| Conversations | `export const dynamic = "force-dynamic"` (no cache; live inbox) |

Avoid `dynamic = "force-dynamic"` on semi-static pages.

### 3. TanStack Query for client cache (when client data is needed)

- Install and wire `@tanstack/react-query` with an **in-memory** QueryClient (no `persistQueryClient` for MVP).
- Use for interactive client islands that need shared cache between navigations.
- Set meaningful `staleTime` (e.g. 5 minutes for customers list) to prevent useless refetches.
- Default query options: sensible `staleTime`, avoid aggressive `refetchOnWindowFocus`.

### 4. Layout persistence via route group

```
app/(app)/layout.tsx   ← sidebar + nav (persists)
app/(app)/dashboard/page.tsx
app/(app)/customers/page.tsx
app/(app)/conversations/page.tsx
app/(app)/campaigns/page.tsx
app/(app)/settings/page.tsx
```

URLs stay flat. Auth gating in this layout is **deferred**.

### Persistence model

1. **Server** — Supabase is source of truth  
2. **Client UI** — localStorage only for light prefs (sidebar, drafts)  
3. **Cache** — TanStack Query (memory); server `revalidate` for RSC pages  

Mental model: **Server = truth · Cache = speed · Client = interaction**

## Consequences

- Positive: faster first paint, less JS, instant-feeling nav, fewer duplicate fetches
- Negative: developers must think about RSC vs client boundaries
- Neutral: Realtime for conversations can layer on later without changing list-page patterns

## Alternatives Considered

1. **Fetch everything on the client, optimize later** — rejected; becomes slow and hard to unwind  
2. **persistQueryClient from day one** — deferred; memory cache is enough for MVP  
3. **Only `/dashboard/layout.tsx`** — rejected; would not persist shell across flat sibling routes  

## Validation

- Shared shell lives in `app/(app)/layout.tsx`
- No `useEffect` primary data fetching in feature pages
- Conversations remain dynamic; other app pages declare `revalidate`
- Agents follow data-layer rules in `AGENT_RULES.md`
